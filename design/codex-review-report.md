评审角色：游戏设计 / 技术架构 / 经文与历史叙事顾问

## 一、结论与评审范围

**建议有条件立项一个缩减的第一关垂直切片，不建议按 v3.0 当前范围直接制作“完全体”或铺开十二章。综合评分：6.0 / 10。** 收束分支适合既定经文故事，资源分配也能承载照顾家族的主题；问题在于新增军事循环压过创13的分离主题，跨章后果改变了创14的事件结构，十二石与应许奖励存在表达混淆。技术栈可用，当前原型距离提案的完整战术系统仍有明显距离。

已完整阅读指定五份源码/文档，并补读 src/App.tsx、src/World.tsx、src/style.css 与 package.json。以下代码判断来自静态审阅；未运行构建、浏览器、真机测试或性能采样。经文判断列出可复核经节，不声称完成新一轮外部史料检索或跨传统审定。本文的预算与验收数字均为建议目标，不能当作实测结果。

评审优先沿用 docs/STORY_HISTORY.md 已有的严格边界：经文事实、历史推断、艺术创作分开；应许不作为玩家绩效奖励；信任只表示协作关系。v3.0 应接受这些约束，而非以新提案覆盖掉它们。

## 二、分支叙事与经文边界

### 2.1 钻石分支成立，但必须固定“经过”中的关键行动

玩家改变照料方式、劳作分配、虚构同伴疲劳和离别代价，是有意义的自由度。跨章在对白、资源配置和一个可用情报上兑现，比为每个选择另做一张地图更经济。风险是把“结局不变”误当成“其余均可改写”：亚伯兰主动求和、罗得先选、罗得被掳后亚伯兰救援，同样属于不能随意反转的叙事骨架。

创13:8–12 的礼让应出现在所有分支共同段落，不能只属于分支 B。“争执失控”若指亚伯兰辱骂、强迫罗得离开，便破坏人物行动；可改成“牧人摩擦未完全平息，匆忙整装”，仍由亚伯兰主动提出和睦分离、罗得自主选择。失羊和关系紧张来自搬迁准备不足，不应宣告玩家选择了道德上不配得到应许的路线。

共同结尾须保留分离之后的应许（创13:14–17），并明确其不取决于和睦分、祭坛亮度或战果。创13:18 迁至幔利的节点可以用短过场承接；不要让夜战“赢得土地应许”。

### 2.2 夏甲 / 乌珥护送罗得：当前版本不应采用

- **夏甲**：创16:1 明确她是撒莱的埃及使女，但文本没有叙述她在创13护送罗得，也没有说她在所多玛承担内应。创12的埃及经历不能自动证明其入家时间、职责或这段任务。把她放在创13并非可直接断言绝对不可能，但只能标为未获经文支持的创作；长期滞留所多玛还需交代如何回到撒莱身边。她有后续核心故事，不适合承担任意死亡、永久离队的系统代价。
- **“乌珥”**：通常首先让读者想到地名。若是虚构人物，应明确标识并考虑改名；若影射已知经文人物，必须给出身份依据，不能默认经文存在这个同伴。
- **以利以谢**：创15:2 提及大马士革人以利以谢；不能由此确定他在创13担任什么职务，更不能直接认定创24未具名老仆必是他。研究文档将其与夏甲列作可承受永久损失的普通同伴，和“经文主干不反转”原则冲突。

**修正**：沿用现有配置中的虚构同伴，以清楚标注的短途护送替代。护送结束即归营；第二关回报为熟悉道路、补给点或一个对白回响，不设置所多玛内应。现代码有七名角色：亚伯兰、撒莱、罗得及以利、努拉、亚撒、玛拉；提案“六名角色”和研究文档另一套人名须先统一。跨时代章节也不能让同一批凡人自然存活数百年，应以独立章节人物与明确时间跳跃组织战役。

### 2.3 “四王前哨斥候”应移出创13

创14:1–12 才交代四王与五王的战争、战役背景和罗得被掳。创13没有亚伯兰与四王前哨交战的记载。提前安排一次“全歼”，再推导四王因而加强防备，会创造一条影响正典战争的军事因果，还让亚伯兰提前掌握危险而没有相应行动。仅写“艺术再创作伏笔”不能消除这种结构性改写。

第一关保留 docs/STORY_HISTORY.md 已声明为虚构的野兽危机即可；如果需要地区不安，可用来历未明的远方烟尘或商旅传闻，不确认四王身份、不提供确定战争预知。真正的敌军侦察、警戒与分兵决策放在创14章节。全歼路线也会把家庭向的非血腥驱离体验突然转为杀人战功，需单独审视年龄分级与主题。

“驱离使敌军轻视，偷袭成功率 +25%”缺乏可靠叙事依据，也未说明是增加 25 个百分点还是相对增加 25%。建议改成一个可见、确定且有限的战术便利，例如揭示一条路线；不让上一章的抽象态度决定救援成败。

### 2.4 创14与创21另有必须纠正的节点

| 提案表述 | 问题 | 建议 |
|---|---|---|
| 罗得城破时撑 5 / 3 回合 | 创14:12–16 是已被掳，逃来的人报信后亚伯兰追击救回；“守城等待”改变救援对象状态 | 第二关开始即承认被掳。可设追踪或被掳队伍转移窗口，但不得容许正典人物因上一关而永久无法救回 |
| 所多玛同伴内应发信号 | 替代或遮蔽创14:13逃来报信者，还制造人质与回归连续性负担 | 保留报信节点；虚构同伴只补充道路信息，不成为消息唯一来源 |
| 麦基洗德献饼酒 vs 拒受所多玛财物 | 创14:18–24 两件事都发生，不能互斥；还应正确交代祝福、十分之一和盟友份额 | 两项共同保留；分支落在虚构同伴安置、归途照料或非正典物资分配 |
| 额外赎回被掳平民 | 创14:16 已说带回妇女和人民，不能把救回他们包装成额外付费善举 | 将可选目标设为额外搜寻散失物资或帮助虚构家庭重整，不减少共同救回结果 |

创14:14–15 支持受训练家丁、追至但、夜间分队攻击；不直接支持盾矛兵编制、火把战术或具体兵种。创21:20 说以实玛利成为弓箭手，不能据此确定复合弓。士20和撒上17支持较晚叙事中的甩石使用，士7支持基甸的火把意象，均不能直接移作亚伯兰装备证据。“机弦手”容易误解成机械发射器，建议称“甩石手”。兵种应标为玩法与时代参考，并按章审阅；石料与青铜也不应在规则上作为可相互替代的一种材料。

### 2.5 限制跨章因果，而非只压缩结局数量

前三次 2×2×3 的选择已有 12 种路径；再乘同伴存亡、伤疲、资源和装备，钻石形地图也会出现文本、平衡与 QA 状态爆炸。

建议第一关仅输出：离别方式一个三值枚举、虚构护送是否完成一个布尔值、一个有上限的后勤等级。原始对白选择保留在只读档案中，不全部参与后续规则。第二关最多读取其中两项，每项只影响一个主要系统；在章末结算后消费或归档，避免十二章叠加永久增益。不要同时叠加“更宽救援窗口 + 内应 + 精锐装备 + 更松警戒”。后果要在选择前说明性质，进入下一章时再明确展示兑现结果。

## 三、四维策略耦合、时长与数值风险

### 3.1 6–12 分钟容得下一个循环，容不下四套独立教程

汲水、伐木、建筑、升级、招募、练兵、选人、排路线、手牌、敌情判断和离别三选一，每项单看简单，合在首关则需要反复切换操作模型。定格后的思考与阅读也计入真实游玩时长，不能只统计模拟执行时间。研究文档末尾“3轮黄昏”与其他段落“2白昼+1夜晚”矛盾，必须统一。

建议第一关按以下预算制作，首次教学允许接近 12 分钟；熟练重玩再瞄准 6–8 分钟：

| 环节 | 目标真实时间 | 玩家主要决定 |
|---|---:|---|
| 抵达与一次分工教学 | 1分钟 | 谁取水、谁备营 |
| 第一白昼 | 2分钟 | 完成一次自动劳作和帐棚准备 |
| 第二白昼 | 1.5分钟 | 物资给防护还是留作离别 |
| 山脊危机 | 2分钟 | 一次站位规划，加一张情境指令 |
| 礼让分离及总结 | 1.5分钟 | 一次有可见代价的离别选择 |

第一关不开放完整练兵树、复合弓手与斥候人类夜战。守望台降为一次临时瞭望岗选择；帐棚与防护设施最多各一次施工。军事在本章体现为家丁护卫职责，第二章再引入最多两类小队与夜间分兵。四维应构成“补给影响准备，准备提供战术，战术改变损耗，损耗影响离别”的短链，而不是四个并列按钮页。

采集建议用“分配一次、阶段结算”，或自动往返至限额，避免逐桶排队。营地经营的主题是资源优先级，不应主要考验重复点击。

### 3.2 需要截断的正反馈和死锁

- 帐棚提高人口上限，人口提高产出，产出继续扩兵，加上祭坛攻防光环，容易让领先者全维度领先。首关固定人口，以有限行动槽形成机会成本；建筑尽量给侧向用途，不同时加产出、回体与战力。
- 强军引发摩擦可以成立，但应说明来自劳力被抽走、牧道维护不足，不能让“训练”神秘地产生争执。民生也应有可靠的危机应对，不应只是为下一关放弃军备。
- 饮水按人口和军队扣费，加上取水需要体力，可能形成缺水→疲劳→无法取水的循环。最低限度取水或撤离必须可用，零资源仍有代价明确的继续路线；没有补救时应明确失败并提供检查点重试。
- 摩擦计时只在模拟推进时增长，定格、阅读、应用切后台均暂停。建议首关分阶段结算，不用惩罚慢阅读者的真实时间倒计时。摩擦满值触发争执或代价，不得强迫罗得选择另一片土地。
- 负面后果应有边界：上关低资源在下关映射为有限后勤劣势，不能使正典救援不可完成。连续两章最差选择也必须可通关，或有清楚的章内重试。

### 3.3 十二圣约祭坛：象征可以保留，实体与奖励必须拆开

创13:3–4 是亚伯兰回到伯特利与艾之间先前筑坛之处；不是本章在伯特利首次新建祭坛。创13:18 在幔利筑坛。经文不交代坛的石数，不能断言该坛只有一块石，也不能宣称由十二石组成。出24:4 的十二根柱子代表十二支派，并与坛有区别；书4的十二石纪念又是另一事件。它们不能被混称为一套自创13连续存在的祭坛。

建议保留两层表现：**场景内呈现该章祭坛或纪念行为；场景外用“十二章旅程纪念石”作为选章界面。** 首次出现时写明：“十二枚纪念石是本作串联各时代故事的艺术象征，并非经文记载的同一座祭坛。”这能解释视觉统一，而不声称跨时代历史实体连续。十二章也不等于十二次圣约；出埃及、战役、水道和修城不能全部命名为一次“立约”。

单关四段用 HUD 环节进度表示，不再每段点亮实体祭坛三块石头。现方案同一个十二石物件既每关全亮又全战役逐石永久亮，含义与重置规则互相冲突。若保留光效，使用无战力收益的回顾动画；回体来自休息、士气来自照顾同伴，避免用“敬拜完成→攻防加成→获得应许”表达交易式神学。第四阶段改称“离别与应许”或“章节回顾”，不把创13称为本章举行了一场新立约仪式。

## 四、手机 UX 与技术架构

### 4.1 屏幕规范可行，但现有实现还未达标

844×390 减去右坞 286px，左侧实际是 558×390，约占 66.1%，并非精确 65%；比例约 1.43，也不是严格 3:2。刘海与横向安全区还会减少可用面积。FOV 30°不能自动保证全营地可见，应根据 Canvas 实际宽高、地图关键点包围盒与遮挡区域求取相机距离和约束。

当前横屏 CSS 已有 286px 坞，但七列头像扣除面板内边距与间距后，每列约 36px 宽，未满足 44px 点击宽度。执行按钮高度 35px、清队列 33px、帮助按钮 25px，同样不达标。竖屏现在是 40dvh 视口（844高时约338px），不是提案的440px；下面区域是页面流式滚动，也不是固定48%操作区。新增练兵与手牌只会进一步把关键信息挤到滚动下方。

研究报告一处要求场景至少62%画面，正式竖屏规范却给52%，两者不能同时作为硬性验收。桌面“全屏3:2”也有歧义：1920×1080全屏不是3:2；必须区分素材比例、沙盘容器与相机取景。现 World 的地面平面为16×12，也不能直接按新3:2底图替换后假设地标仍对齐。

### 4.2 推荐操作减负

1. **默认点选角色→点目标→确认；拖线为可选增强。** 单指拖动只平移镜头；进入明确规划模式后才编辑路径。设置移动阈值、pointer capture、取消和撤销，拖动结束不得产生地面移动点击。
2. **手机默认单选，长按或明确按钮进入编组。** 当前头像点击是不断累积多选，容易把汲水、施工指令广播给全队。首关只要求同时调度2–3个职责组，兵士以小队代表，不逐人排线。
3. **坞内按情境切换。** 白昼只显示劳作与建设，危机只显示护卫与至多3张情境指令；执行/定格和选择状态固定可见。头像横滑，每项至少44×44，优先48；说明点击展开，不依赖悬停。
4. **把手牌当作行动命令入口。** 显示资源成本、目标和预期效果，避免抽牌、弃牌、冷却另添一套规则。预览后确认扣费；执行失败要说明原因并可重新规划。
5. **镜头跟随不能抢控制。** 选人只平滑定位一次，手动拖动后暂停跟随；快捷地标可达屏外对象，执行时可切全局。当前 CameraRig 每帧跟随 selected[0]，将直接抵消新增自由平移。

竖屏440px场景高度可作为起点，但应基于安全区后的可用高度，而非固定像素相加；下方只保留一层主要内容。旋屏须保留选择、队列和暂停状态，重新计算 Canvas 尺寸与投影。夜景保证角色、路径、敌情的对比度，不以纯黑遮蔽替代战术信息；颜色之外增加形状与文本提示。

### 4.3 现有模拟层的具体缺口

| 代码证据 | 风险与建议 |
|---|---|
| App 每80ms调用 tick；移动每次固定0.16 | 名义速度约2世界单位/秒，但后台节流和低帧率会改变实际推进。使用固定模拟步长与渲染插值，限制追帧；页面隐藏默认暂停 |
| tick 无队列或全员无体力就直接返回 | 新昼夜不能继续复用此提前返回，否则空闲可冻结摩擦和耗水。将阶段时钟与任务推进拆开 |
| energy≤0 的角色连 rest 都不处理 | 真实的恢复死锁；增加救助/被动最低恢复或允许休息恢复。不能仅在UI上提示休息 |
| 同一地点可连续采集、反复build | 当前不要求回营卸载，load未使用；建帐棚没有槽位上限，资源/帐棚/信任可刷。明确采集周期、阶段额度、建造容量和一次性奖励 |
| 同帧用 actors.map 顺序修改公共资源 | 最后一份水给谁由数组顺序决定；建造/手牌需统一验证、预留、结算和冲突说明 |
| scout发现后仅在tick结尾置 paused | 同tick后面的角色仍可能继续任务甚至结束遭遇。关键事件应成为原子转换，先确定优先级再停表 |
| Game只有 story/encounter 少量枚举 | 无昼夜、军队、伤疲、祭坛、战役结果。不要在两个文件堆全部逻辑；拆分关卡定义、模拟规则、战役摘要、存档和表现适配 |
| Game.version为1，存储键尾缀v2；loadGame检查很少 | 新版需显式schemaVersion和迁移/重置说明，校验坐标、队列、资源范围及枚举；校验失败的存档不应冒充正常可续玩状态 |

建议以显式阶段状态机组织“抵达→白昼一→白昼二→危机→分离→回顾”。规则产生领域事件，由界面展示；结局选择也应从 App.resolve 移入规则层，统一校验费用与经文锚点。暂停时允许编辑命令，执行时按稳定规则提交。跨章仅存摘要，不继承整份上一章 Game。

### 4.4 React / Three.js 的性能边界

Vite是构建工具；React负责界面、Three.js负责沙盘，足以支撑小规模2.5D。Capacitor提供原生容器，不会自动解决WebGL预算、触控或双端布局。现七角色规模没有证据表明已出现性能瓶颈，但不能把它线性扩大成318个独立单位。

当前每个角色16×24分段平面约425顶点，每帧CPU形变；七人约2975顶点本身不算大，扩成大量士兵后才需优先改成着色器动画、少帧贴图或小队实例化。路径几何依赖位置，每次逻辑移动都会重新创建并释放；可复用BufferGeometry。CameraRig每帧创建Vector3也可复用，但优先级低于新增大粒子、透明叠加和全局重绘。

App每次game改变即同步JSON写localStorage；运行时可能约每秒12.5次。建议在阶段转换、命令提交、暂停和应用生命周期时保存，必要时防抖，保留最后有效检查点；移动中断恢复默认暂停。模拟高频位置用ref或独立store，HUD只订阅必要摘要，避免扩军后整个控制面板同步频繁重渲染。

Canvas当前dpr上限2、抗锯齿开启且请求high-performance，连续执行useFrame。低档手机先限制DPR到1–1.5，优先透明度/发光材质与轻量光晕，避免默认Bloom、动态阴影和大量点光源。暂停但仍有动画时不能机械切换到frameloop=demand后不再刷新；应降低环境动画频率，或正确调度invalidate。退到后台停渲染，处理WebGL上下文丢失。

建议立项目标：目标中低档真机交战稳定30fps（帧预算33.3ms），输入到反馈尽量≤100ms；这些需实测。用模拟满负载场景、连续三局和前后台恢复检查热量、内存增长与长帧。浏览器截图只能确认布局，不能证明触控可靠或真机性能。

## 五、证据质量与立项验收

RESEARCH_AND_SCREEN_SPEC.md 引用营收、销量、游玩时长及“竖屏赢D1、横屏赢D7–D30”，但没有可追溯链接、样本、口径与测试条件。竞品商业表现不能证明本项目的时长和方向选择，更不能把相关性写成“硬性科学规律”。这些结论目前只能作为待检验假设；立项前补出处，无法补证的改为设计判断。本文不认可或复述其中数字为已核实事实。

推荐验证顺序：先纸面复核全部锚点和十二种首关路径，再制作只含一套危机的可玩切片，然后做横竖屏触控观察。关键规则测试应覆盖零资源、零体力、同帧争用、事件暂停、最差跨章输入与坏存档；不需要为每条纯文案另写测试。构建通过之后仍须真机验证，当前评审不替代任何这些检查。

建议小规模试玩至少记录：首次完成时间（包含阅读）、无协助完成比例、误选与误发指令次数、手牌发现率、关键成本理解程度。首轮可将“多数首次玩家12分钟内完成，能解释一次选择代价”作为方向性门槛；小样本不用于宣称留存提升。第二章用最佳/最差两组继承状态各跑一遍，验证没有必选路线和软死锁。
